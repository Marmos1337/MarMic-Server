# MarMic Server Privacy & Telemetry Policy

Этот документ описывает предполагаемую техническую телеметрию self-hosted MarMic Servers и принципы её обработки центральной инфраструктурой MarMic.

## Основной принцип

MarMic Server работает на инфраструктуре владельца сервера.

MarMic не должен использовать server telemetry для получения содержимого частных коммуникаций пользователей.

Техническая телеметрия предназначена для:

- совместимости;
- обновлений;
- диагностики;
- безопасности;
- стабильности;
- развития продукта;
- предотвращения злоупотреблений;
- работы глобальной инфраструктуры MarMic.

## Данные регистрации сервера

При регистрации MarMic Server центральная инфраструктура может получать и хранить:

- уникальный `server_id`;
- публичный ключ сервера;
- технический hostname;
- публичный IPv4 и/или IPv6;
- версию MarMic Server;
- операционную систему;
- архитектуру процессора;
- дату регистрации;
- дату последнего соединения;
- состояние регистрации;
- тип лицензии;
- состояние DNS;
- информацию о владельце после выполнения Owner Claim.

Private key сервера не должен передаваться в MarMic Hub.

## Техническая телеметрия

MarMic Server может передавать:

- версию MarMic Server;
- версию installer/update agent;
- OS и architecture;
- версии необходимых runtime-компонентов;
- версию Docker, если он используется;
- версию LiveKit;
- uptime;
- health status;
- информацию об успешных и неуспешных обновлениях;
- технические коды ошибок;
- сведения о совместимости;
- объём доступного дискового пространства;
- использование CPU/RAM в техническом виде;
- агрегированное количество пользователей;
- агрегированное количество каналов;
- другую минимально необходимую техническую информацию.

Состав телеметрии может развиваться вместе с продуктом.

При добавлении существенно новых категорий данных эта политика должна обновляться.

## Что MarMic Server telemetry не предназначена собирать

Обычная техническая телеметрия не должна включать:

- текст пользовательских сообщений;
- содержимое Direct Messages;
- голосовые разговоры;
- видеопотоки;
- screen share;
- содержимое загруженных файлов;
- пароли пользователей;
- authentication tokens;
- Owner Token в открытом виде;
- private key сервера;
- содержимое локальной базы данных сервера.

Некоторые центральные функции MarMic Identity и Hub могут обрабатывать собственные данные, необходимые для глобальной аутентификации и работы сервиса. Они должны рассматриваться отдельно от технической телеметрии self-hosted сервера.

## Public IP и DNS

Публичный IP сервера может передаваться MarMic Hub, поскольку он необходим для:

- выдачи технического поддомена;
- обновления DNS;
- DDNS при изменении домашнего внешнего IP;
- проверки доступности инфраструктуры.

Например, сервер может получить:

`xxxxxxxxxxxxxxxxxxxx.srv.mic.marhub.ru` (new installations; legacy servers
may retain their original `srv.marmic.udav.team` alias)

При изменении IP DNS-запись может быть автоматически обновлена.

Обновление DNS может занимать до 10 минут.

## Owner Identity

После активации Owner Token глобальный MarMic Identity владельца связывается с соответствующим `server_id`.

Это используется для:

- определения владельца;
- управления сервером;
- уведомлений;
- подтверждения крупных обновлений;
- будущих функций управления self-hosted инфраструктурой.

## Server Directory

Архитектура MarMic может поддерживать будущий публичный каталог серверов.

Предполагаемые режимы видимости:

- `private`;
- `unlisted`;
- `public`.

По умолчанию сервер не должен автоматически публиковаться в глобальном каталоге без соответствующей настройки.

Сам публичный каталог может быть реализован отдельно в будущем.

## Обновления

Server Registry и update infrastructure могут хранить:

- текущую версию сервера;
- доступную версию;
- состояние обновления;
- результат установки;
- результат migration;
- результат health check;
- информацию о rollback.

Это необходимо для безопасной доставки обязательных patch/security updates и крупных migration-sensitive обновлений.

## Техническая поддержка

MarMic не предусматривает скрытого административного доступа к VPS или домашнему серверу пользователя.

Если в будущем будет реализован remote support, он должен:

- явно включаться владельцем;
- иметь ограниченный срок действия;
- отображаться владельцу;
- автоматически отключаться;
- предоставлять только необходимый объём доступа.

## Безопасность

Credentials, private keys и другие секретные данные не должны передаваться в обычной телеметрии.

Диагностические команды, включая будущий `marmic doctor`, должны по возможности автоматически скрывать секреты перед выводом диагностической информации.

## Изменения политики

Эта политика может обновляться по мере развития MarMic.

Существенные изменения состава собираемых данных должны отражаться в новой версии документа.
