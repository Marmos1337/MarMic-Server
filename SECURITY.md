# MarMic Security Policy

## Поддерживаемые версии

MarMic развивается как единая client/server platform.

Актуальные stable-версии получают:

* исправления безопасности;
* compatibility fixes;
* обязательные patch updates;
* обновления server infrastructure.

Старые версии могут перестать поддерживаться, если они несовместимы с актуальной инфраструктурой или содержат известные проблемы безопасности.

MarMic может устанавливать `minimumSupportedVersion`.

## Сообщение об уязвимости

Не публикуйте сведения о серьёзной уязвимости в открытом Issue до того, как у разработчика была возможность её проверить и исправить.

Предпочтительный способ сообщения:

1. Использовать GitHub Private Vulnerability Reporting / Security Advisory в официальном репозитории MarMic, если функция доступна.
2. Если этот способ недоступен — использовать официальный приватный контакт MarMic.

В сообщении желательно указать:

* затронутую версию;
* компонент;
* описание проблемы;
* шаги воспроизведения;
* возможное влияние;
* proof of concept, если он безопасен;
* предполагаемое исправление, если оно известно.

Не передавайте реальные пользовательские secrets или персональные данные, если для воспроизведения достаточно тестовых данных.

## Server Identity

Каждый зарегистрированный MarMic Server должен иметь собственную криптографическую identity.

Предполагаемая модель:

* keypair генерируется непосредственно на сервере;
* private key не покидает сервер;
* Hub получает только public key;
* сервер доказывает владение private key через challenge-response;
* challenge имеет ограниченный срок действия;
* replay старых challenge должен быть невозможен.

Server credentials должны храниться отдельно от runtime, чтобы обновление приложения не уничтожало server identity.

## Owner Token

Первоначальный владелец сервера получает одноразовый Owner Token после установки.

Owner Token должен:

* генерироваться криптографически безопасным способом;
* иметь ограниченный срок действия;
* быть одноразовым;
* храниться серверной инфраструктурой только в безопасной форме;
* инвалидироваться после успешного claim;
* инвалидироваться после regeneration.

Пока сервер не имеет владельца, новый токен может быть создан локально через административную CLI-команду.

После успешного claim сервер не должен допускать повторный захват владельца другим пользователем через старый Owner Token.

## Updates

Официальные server updates должны проверяться до установки.

Предполагаемая схема:

1. Получить release manifest.
2. Проверить цифровую подпись manifest.
3. Скачать официальный runtime.
4. Проверить checksum.
5. Выполнить backup/preflight при необходимости.
6. Выполнить update.
7. Выполнить migration при необходимости.
8. Выполнить health check.
9. Выполнить rollback при критическом failure.

Release-signing private key не должен находиться на self-hosted MarMic Servers.

Server runtime должен содержать только необходимые public verification keys.

## Обязательные обновления

Security и compatibility patches могут быть обязательными.

Владелец сервера не должен иметь возможность навсегда отключить обязательные обновления.

При этом обновление должно по возможности избегать неожиданного прерывания активного использования.

Для критических security updates может использоваться обязательный deadline.

## Крупные обновления

Migration-sensitive обновления должны рассматриваться отдельно от обычных patch updates.

Перед их установкой должны быть предусмотрены:

* уведомление владельца;
* backup;
* проверка состояния базы;
* проверка свободного места;
* migration preflight;
* health check;
* rollback path.

## DNS Credentials

Credentials для управления глобальной DNS-зоной MarMic никогда не должны передаваться self-hosted серверам.

Схема должна быть:

`MarMic Server → authenticated Hub request → MarMic Hub → DNS provider API`

Только доверенная центральная инфраструктура MarMic хранит credentials DNS-провайдера.

## Secrets

Запрещается хранить secrets:

* в Git repository;
* в публичных конфигурациях;
* в Docker images;
* в документации;
* в CI logs;
* в диагностических отчётах;
* в crash reports.

Production secrets должны передаваться через предназначенное для этого secret/configuration storage.

Файлы с локальными secrets должны иметь ограниченные filesystem permissions.

## Self-hosted Data

Runtime, конфигурация и пользовательские данные должны быть разделены.

Рекомендуемая архитектура:

`/opt/marmic/` — runtime
`/etc/marmic/` — configuration
`/var/lib/marmic/` — database, files и server identity
`/var/backups/marmic/` — backups

Обновление runtime не должно удалять пользовательские данные или server identity.

## Database Safety

Перед чувствительными migrations должны выполняться соответствующие проверки целостности базы данных.

Для SQLite могут использоваться:

* `PRAGMA quick_check`;
* foreign key checks;
* backup перед migration.

Ошибочная migration не должна автоматически уничтожать последнюю рабочую копию данных.

## Remote Access

В официальный MarMic Server не должен встраиваться скрытый постоянный remote shell или backdoor.

Если remote support будет реализован, он должен быть:

* явно включён владельцем;
* временным;
* ограниченным по полномочиям;
* видимым владельцу;
* автоматически истекающим;
* журналируемым в разумных пределах.

## Telemetry Security

Телеметрия не должна использоваться для передачи:

* authentication tokens;
* private keys;
* Owner Token;
* содержимого сообщений;
* голосовых или видеоданных;
* содержимого пользовательских файлов.

Диагностические инструменты должны автоматически редактировать известные секретные значения перед выводом.

## Network Security

MarMic Server должен использовать защищённые transport protocols для внешнего управления и API.

Публичные server endpoints должны использовать HTTPS/TLS.

Для домашних установок владелец может быть обязан настроить port forwarding и firewall согласно официальной документации.

Официальная документация должна перечислять только реально необходимые порты.

## Rate Limiting

Публичные Registry endpoints должны иметь защиту от автоматизированных злоупотреблений.

Она может включать:

* IP rate limiting;
* registration rate limiting;
* challenge expiration;
* replay protection;
* ограничения на abandoned registrations;
* cleanup неактивированных DNS entries.

Ограничения не должны предполагать, что один IP всегда соответствует одному пользователю, поскольку NAT и hosting infrastructure могут обслуживать несколько серверов.

## Dependency Security

Сторонние зависимости должны:

* фиксироваться в reproducible dependency manifests;
* обновляться при известных критических уязвимостях;
* использоваться в соответствии с собственными лицензиями.

Информация о сторонних лицензиях публикуется в `THIRD_PARTY_NOTICES.md`.

## Security Changes

MarMic может изменять security architecture по мере развития продукта, если это необходимо для устранения уязвимостей, повышения безопасности или совместимости.
